## 需求與原因

學習紀錄原本只存在瀏覽器，換裝置要手動用備份檔或代碼搬。使用者希望 Google 登入一次就能在多台裝置延續紀錄，並且能控制誰可以使用。

不在範圍：Tauri APP 的登入與同步、逐題事件合併、自訂網域、端到端加密、`_headers` 安全標頭、擁有者轉讓。既有 Google Drive 手動備份不動。

## 變更前與變更後

| 情境 | 變更前 | 變更後 |
|---|---|---|
| 主機 | GitHub Pages 純靜態 | Cloudflare Workers：靜態資源＋同網域 `/api/*`；GitHub Pages 舊站保留並顯示搬家提示 |
| 未登入使用者 | 本機學習 | 完全相同；雲端網址只多一次 `GET /api/me`，不載入任何 Google 腳本 |
| 登入 | 無 | 伺服器端授權碼＋PKCE；HttpOnly `__Host-` session cookie（30 天）；只有白名單或開放模式的已驗證 email 能登入 |
| 存取控制 | 無 | D1 白名單，增刪即時生效；三層角色：擁有者（只能用 SQL 設定、後台不能移除或降級）、管理員（只能新增成員）、成員 |
| 跨裝置 | 手動備份檔／代碼 | 登入後自動上傳整份快照；雲端以 revision 防止互相覆蓋；只有一邊變動時提示套用，兩邊都變時由使用者選擇；不合併 |
| 清除紀錄或匯入後 | — | 不自動覆蓋雲端，先詢問是否也更新雲端 |
| 發布範圍 | GitHub Pages 發布整個 repo | Workers 版以白名單只發布網站檔案（`tools/build-site.mjs` → `dist-site/`） |

## 規則、邊界與取捨

- 正常路徑：見設計 §2.3；同步判斷集中在 `core/cloud-sync.js` 的 `decide()`。
- 空資料、失敗、取消、重試與競態：
  - 上傳 10 秒防抖、頁面隱藏立即上傳；失敗以 30 秒、1、2、5 分退避，之後每 5 分。
  - 上傳結果不明時先查 meta，以 `uploadId` 判斷是否已成功。
  - 同裝置多分頁以 Web Locks 保證只有一個在上傳。
  - 伺服器條件式寫入用單一 `db.batch()`，兩個同基準上傳只會成功一個，失敗方不留分塊。
- 實作時的補充（規格未寫明，偏保守）：
  - 雲端 revision 比同步基準舊（雲端被刪）時，作廢基準，回到第一次同步的規則。
  - 本機整組替換且雲端也較新時，判為衝突，不走「是否更新雲端」的詢問。
  - 「上傳結果不明」只記在記憶體；送出後立刻關頁，下次開啟可能多跳一次衝突選擇，不會遺失資料。
  - 管理員移除擁有者時，`OWNER_PROTECTED`（409）優先於 `OWNER_ONLY`（403）；擁有者可以改自己的暱稱，409 只用在移除與改角色（tasks 原文「任何以擁有者為對象的操作回 409」與 M07、M08 衝突，依規格處理）。
- 平台差異：雲端功能只在 `assets/js/config/cloud.js` 設定的新網址啟用；舊站、本機 `serve` 與 APP 一律關閉。`privacy.html` 與 `admin.html` 只屬網站版，不打包進 APP，所以說明頁不放靜態連結，由網站版的雲端畫面動態加上。
- 取捨：
  - 選 D1 分塊而不是 R2：同一交易、不用綁付款方式。代價是單一資料庫 500 MB 上限。
  - 選整份快照而不是事件合併：兩台裝置同時練習時，只能保留一邊的新進度。
