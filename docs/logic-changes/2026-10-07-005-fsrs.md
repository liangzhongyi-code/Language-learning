## 需求與原因

B 階段需要可離線、可重現且可追溯版本的 FSRS 排程，同時保留原始累計與按能力、方向隔離的狀態。不能由舊作答次數推造記憶參數，也不能把提示、重試或重播音訊臆測成 Hard／Easy。

## 變更前與變更後

原有核心使用 Leitner：合格答對升盒、答錯重設盒號；FSRS 狀態無法交給這個政策處理。工作區現在由共用逐題交易組件 `reviewChanges` 明確傳入 `policy: 'fsrs'`。`scheduleReview` 與 `applyReview` 的預設值仍是 `leitner`，並非所有直接呼叫核心的路徑都自動改用 FSRS。

新能力仍由原初始化器建立；只有第一次符合排程資格的實際作答，才由 adapter 建立 FSRS 狀態。舊 Leitner／legacy 能力也在合格複習時轉換；未到期的 Good 保持原 due 與舊排程，未到期的首次合格 Again 則可以轉換。來源摘要累計繼續更新，FSRS 合格排程只同步摘要 due，保留原 box。

## 規則、邊界與取捨

- 上游為 `ts-fsrs` 5.4.2，應用狀態版本為 `ts-fsrs-5.4.2-d1`。使用上游預設參數，另明確關閉 `enable_fuzz` 與 `enable_short_term`；不訓練個人參數。d1 使用天級間隔，不沿用 Leitner 對齊本地午夜的計算。
- 無提示且沒有 retry 的答對為 Good；答錯、提示或 retry 為 Again。真實 correct 統計仍依原判題，提示答對不改成答錯；replayCount 與 responseMs 不產生 Hard／Easy。
- 資格判定限同 session、同 skillKey：Good 必須到期且該局尚無合格排程；Again 在該局尚無合格 Again 時可以重設一次；明確 reinforcement 不改長期排程。這是目前的「當局」限制，不宣稱已做跨 session 的同日去重。重送題次由 repository 收據處理，核心遇到重複 entry／review 則拒絕再次計數。
- FSRS 狀態只存 JSON 數值與毫秒時間，包含 stability、difficulty、elapsedDays、scheduledDays、reps、lapses、learningSteps、state、lastReview；不持久化 Date。d1 已提交卡片必須為 Review、learningSteps 為 0；Review 且 stability 至少 90 天標為 mastered，其餘 Review 為 review。Again 不等於一律標為 learning，也不等於一律取消 mastered，應依實際輸出判定。
- adapter 在資格判定前驗證既有 FSRS 狀態，所以未到期或補強也不能繞過未知版本、非有限數值、不合法計數、額外欄位或時間限制。錯誤使用 `INVALID_DATA`／`UNSUPPORTED_VERSION`；FSRS 狀態交給 Leitner 政策則為 `UNSUPPORTED`。計算不修改傳入狀態；adapter 的拒絕結果不代表本次已驗證所有真瀏覽器交易故障。
- vendor 是 `assets/js/vendor/ts-fsrs.js`，執行期從本機 ES module 載入，沒有 CDN。`tools/build-fsrs.mjs` 核對精確版本、MIT 授權與固定來源 SHA-256 後，針對該來源將 class fields 移至 constructor 的 DefineProperty 初始化，保留 own-property descriptor 與初始化順序；移除 sourceMappingURL 並加上完整 MIT 與來源／輸出雜湊。這不是通用轉譯器，來源漂移會停止建置。
